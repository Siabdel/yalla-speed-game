## 1. Étude de faisabilité

### 1.1 « Moteur Blender » : ce qui est réaliste

Il faut d'abord lever une ambiguïté : **Blender n'est pas un moteur de jeu web**. Le Blender Game Engine (BGE) a disparu, et faire tourner Blender lui-même dans le navigateur via WebAssembly est **techniquement possible mais expérimental et très lourd** (projets comme `blender-wasm` ou `@volter/cyclotron`, qui compile Blender 5.2 en WASM pour servir d'éditeur, pas de runtime de jeu léger). Pour un jeu destiné à de jeunes enfants, ce serait disproportionné en temps de chargement et en consommation mémoire.

La chaîne **réaliste et éprouvée** est donc la suivante :

> **Blender = atelier de création d'assets 3D** (voiture, circuit, panneaux, décor, animations) → **export glTF/GLB** → **Three.js ou Babylon.js = moteur de rendu et de jeu dans le navigateur** → **Vue.js = interface (menus, quiz, HUD, résultats)**.

C'est exactement le pipeline recommandé par la documentation actuelle : Blender produit du glTF/GLB, et les moteurs web (Three.js, Babylon.js, React Three Fiber, PlayCanvas) consomment ces fichiers. Il existe même des skill/plugins « Blender web pipeline » spécifiquement conçus pour automatiser l'export optimisé vers Three.js/Babylon.js.

**Conclusion sur ce point :** la partie 3D de la course est **faisable et standard**. Le seul « risque » est de vouloir exécuter Blender *dans* le navigateur ; il faut l'écarter pour le runtime et le garder comme outil de production.

### 1.2 IA légère pour la voix et la transcription, dans le navigateur

Deux briques sont nécessaires : **STT** (reconnaissance vocale pour répondre aux quiz/devinettes) et **TTS** (synthèse vocale pour lire les consignes, les indices, les panneaux en arabe/anglais).

**Transcription (STT) — faisable et mature.**
Des bibliothèques TypeScript exécutent Whisper **entièrement dans le navigateur**, avec WebGPU (repli WASM), sans backend ni clé API. `browser-whisper` télécharge des modèles de ~80 Mo (`whisper-base`) à ~510 Mo (`whisper-small`), supporte ~100 langues (dont arabe et anglais), et met en cache les poids dans l'OPFS pour un usage hors-ligne après le premier chargement. Pour un jeu enfant, un modèle `base` ou `small` suffit largement pour reconnaître quelques mots ciblés, avec un vocabulaire contraint (les réponses attendues sont connues à l'avance).

**Synthèse vocale (TTS) — faisable, avec une nuance pour l'arabe.**
`Kokoro-js` fait tourner le modèle **Kokoro (82 M paramètres)** localement dans le navigateur via Transformers.js, avec WebGPU ou WASM, et produit de la parole de qualité en temps réel. Le modèle original couvre principalement l'anglais, le français, l'espagnol, l'hindi, l'italien, le portugais, le japonais et le chinois. **L'arabe n'est pas une langue native de Kokoro standard**, mais il existe des **fine-tunings communautaires** (par exemple `Nabra-82M`, Kokoro fine-tuné pour l'arabe standard moderne) et des pipelines `sherpa-onnx` qui ajoutent un front-end arabe.

**Solution pragmatique pour l'arabe :**
1. Utiliser d'abord la **Web Speech API** (`SpeechSynthesis`) du navigateur, qui supporte l'arabe (de nombreux dialectes/voix régionales) sur Chrome/Edge/Safari, sans téléchargement de modèle et avec une latence quasi nulle. C'est la voie la plus simple pour démarrer.
2. Si l'on veut une voix **hors-ligne, constante et de meilleure qualité**, intégrer un TTS neuronal léger spécialisé arabe/anglais (Nabra-82M ou un modèle ONNX équivalent) dans le même pipeline que Kokoro-js. Cela reste dans l'ordre de grandeur de 100–200 Mo.

**Conclusion sur ce point :** l'IA légère **est faisable 100 % côté navigateur**, sans serveur GPU. Le seul compromis est le support natif de l'arabe en TTS, qui se règle soit par la Web Speech API (immédiat), soit par un modèle fine-tuné (plus de travail mais hors-ligne).

### 1.3 Faisabilité globale du jeu

| Brique                             | Faisabilité | Risque principal                     | Parade                                                       |
| ---------------------------------- | ----------- | ------------------------------------ | ------------------------------------------------------------ |
| Course 3D avec circuit et panneaux | ✅ Élevée    | Performance sur PC modestes          | Low-poly, GLB optimisés, LOD, pas d'ombres dynamiques coûteuses |
| Quiz / devinettes avec voix        | ✅ Élevée    | Qualité STT en environnement bruyant | Vocabulaire fermé, bouton « répéter », tolérance aux erreurs |
| TTS arabe/anglais                  | ⚠️ Moyenne   | Arabe non natif dans Kokoro standard | Web Speech API en v1, TTS fine-tuné en v2                    |
| STT arabe/anglais                  | ✅ Élevée    | Téléchargement initial du modèle     | Préchargement + cache OPFS, modèle `base`                    |
| Score, progression, résultats      | ✅ Élevée    | Aucun                                | Stockage local (IndexedDB) ou backend léger                  |
| Mode hors-ligne                    | ✅ Élevée    | Première visite                      | Service Worker + cache des modèles                           |

**Verdict :** le projet est **faisable avec une complexité modérée**, à condition de **ne pas essayer d'exécuter Blender dans le navigateur** et de **traiter l'arabe TTS via la Web Speech API en première intention**.

## 2. Architecture proposée

### 2.1 Vue d'ensemble

```
┌──────────────────────────────────────────────────────────────┐
│                        NAVIGATEUR (client)                    │
│                                                              │
│  ┌────────────────┐      ┌──────────────────────────────┐   │
│  │   Vue.js 3      │◄────►│  State global (Pinia)         │   │
│  │  (UI, menus,    │      │  score, progression, langue,  │   │
│  │   quiz, HUD)    │      │  résultat de la course        │   │
│  └───────┬────────┘      └──────────────────────────────┘   │
│          │                                                    │
│  ┌───────▼──────────────────────────────────────────────┐    │
│  │              Couche « Game Runtime »                  │    │
│  │  Three.js (scène, physique simple, contrôles)         │    │
│  │  + logique de course (checkpoints, panneaux, score)  │    │
│  └───────┬──────────────────────────────────────────────┘    │
│          │                                                    │
│  ┌───────▼──────────────┐   ┌────────────────────────────┐   │
│  │  Assets GLB/GLTF      │   │  Modules IA locaux         │   │
│  │  (exportés de Blender)│   │  STT : browser-whisper     │   │
│  │  voiture, circuit,    │   │  TTS : Kokoro-js / Web     │   │
│  │  panneaux, décor      │   │        Speech API          │   │
│  └──────────────────────┘   └────────────────────────────┘   │
│                                                              │
│  ┌────────────────────────────────────────────────────────┐ │
│  │  Stockage local : IndexedDB (scores) + OPFS (modèles)  │ │
│  └────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────┘
```

**Aucun serveur n'est strictement nécessaire** pour la v1 : les modèles IA, les assets 3D et les scores peuvent rester côté client. Un backend léger (Django/DRF ou FastAPI) n'est utile que si l'on veut **synchroniser les scores entre appareils**, **gérer des comptes parents** ou **mettre à jour le contenu pédagogique à distance**.

### 2.2 Choix techniques recommandés

| Couche                               | Technologie                                                  | Justification                                                |
| ------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **UI / logique applicative**         | **Vue.js 3** + Pinia + Vue Router                            | Stack demandée, écosystème mature, réactivité idéale pour les quiz et le HUD |
| **Rendu 3D / course**                | **Three.js** (ou Babylon.js)                                 | Standard pour les jeux 3D web ; Three.js est plus léger et mieux documenté pour un premier jeu |
| **Physique simple**                  | **Cannon-es** ou **Rapier** (WASM)                           | Pour une course de voitures, une physique arcade suffit ; Cannon-es est simple et bien intégré à Three.js |
| **Création des assets**              | **Blender** (hors navigateur)                                | Modélisation low-poly, export **glTF 2.0 / GLB** avec matériaux et animations |
| **Transcription vocale**             | **browser-whisper** (`whisper-base` ou `small`)              | 100 % local, WebGPU + WASM, ~80–510 Mo, cache OPFS, supporte l'arabe et l'anglais |
| **Synthèse vocale (v1)**             | **Web Speech API**                                           | Zéro téléchargement, supporte l'arabe sur navigateurs modernes, idéal pour prototyper |
| **Synthèse vocale (v2, hors-ligne)** | **Kokoro-js** (anglais) + **Nabra-82M** ou équivalent ONNX (arabe) | Voix neuronales locales, qualité supérieure, fonctionne sans réseau |
| **Stockage**                         | **IndexedDB** (scores, progression) + **OPFS** (modèles IA)  | Persistance locale sans backend                              |
| **Build**                            | **Vite**                                                     | Rapide, standard avec Vue.js                                 |

### 2.3 Découpage en modules

**A. Module « Course »**
- Circuit généré à partir d'un **GLB exporté de Blender** (route, décor, checkpoints).
- Voiture contrôlée au clavier/tactile (flèches ou boutons virtuels).
- **Panneaux de signalétique** placés le long du circuit : chaque panneau affiche un mot ou un symbole en **arabe** ou en **anglais** (ex. « droite », « gauche », « stop », « école »). L'enfant doit **s'orienter dans la bonne direction** en fonction du panneau pour valider un checkpoint et gagner des points.
- Physique arcade simple : accélération, freinage, direction, collisions avec les bords (Cannon-es).
- Chronomètre, compteur de checkpoints, score en temps réel affiché dans le **HUD Vue.js** (superposé au canvas Three.js).

**B. Module « Quiz / Devinettes »**
- Écran 2D en Vue.js (pas de 3D nécessaire).
- Question affichée en texte + **lue à voix haute** via TTS (arabe ou anglais selon le mode).
- L'enfant répond :
  - soit en **cliquant** sur une image/bouton,
  - soit **à l'oral** (le STT transcrit, on compare à la réponse attendue avec une tolérance).
- Feedback immédiat : son de réussite/échec, animation, points.
- Les questions sont stockées dans un **fichier JSON local** (facilement modifiable par un parent/enseignant).

**C. Module « IA locale »**
- **STT** : chargement paresseux de `browser-whisper` au premier besoin ; préchargement possible depuis l'écran d'accueil. Langue configurable (`ar` ou `en`).
- **TTS** : abstraction `speak(text, lang)` avec deux implémentations interchangeables : `WebSpeechTTS` (par défaut) et `KokoroTTS` / `NabraTTS` (hors-ligne). Le jeu choisit automatiquement selon la disponibilité.
- Gestion du **contexte audio** : ne jamais superposer TTS et sons du jeu ; file d'attente ou interruption propre.

**D. Module « Progression et résultats »**
- Score global, étoiles par niveau, déblocage de circuits/voitures.
- Panneau de résultats en fin de course/quiz : points, précision, temps, mots appris.
- Stockage dans **IndexedDB**.
- Option : export JSON pour le parent.

### 2.4 Pipeline de production des assets (Blender → Web)

1. **Modélisation low-poly** dans Blender : voiture, éléments de circuit, panneaux (avec textures ou matériaux colorés), décor.
2. **Nommage rigoureux** des objets (ex. `Car`, `Track`, `Sign_Right`, `Sign_Left`, `Checkpoint_01`) pour que le code Three.js les retrouve facilement.
3. **Export glTF 2.0 / GLB** avec :
   - matériaux PBR simples (pas de shaders complexes),
   - textures compressées (KTX2 si possible, ou PNG optimisés),
   - animations de la voiture (roues qui tournent, suspension) incluses dans le GLB.
4. **Optimisation** : limiter le nombre de polygones, fusionner les matériaux, utiliser des LOD si le circuit est grand.
5. **Intégration** : charger le GLB avec `GLTFLoader` de Three.js ; le code de jeu manipule les objets nommés.

## 3. Cahier des charges pour Claude Code

### 3.1 Objectif général

Développer une **application web éducative** permettant à des enfants (5–10 ans) d'apprendre l'**arabe** et l'**anglais** via trois activités : **quiz**, **devinettes** et **course de voitures avec signalétique**. L'application fonctionne **dans le navigateur**, sans backend obligatoire, avec **voix et transcription locales**. La 3D est produite dans Blender puis exportée en glTF/GLB ; le runtime utilise **Three.js** et l'interface **Vue.js 3**.

### 3.2 Spécifications fonctionnelles

**F1 — Gestion des langues**
- L'utilisateur (ou le parent) choisit la langue cible : **arabe** ou **anglais**.
- L'interface peut rester en français (ou être traduite) ; seule la langue *apprise* change.
- Les contenus (mots, questions, panneaux, voix) sont disponibles dans les deux langues.

**F2 — Mode Quiz**
- Afficher une question avec 3 ou 4 propositions (images ou texte).
- Lire la question à voix haute dans la langue cible.
- L'enfant peut répondre par clic ou par voix.
- Feedback immédiat (son, animation, points).
- Série de 5 à 10 questions par session.
- Écran de résultats en fin de session.

**F3 — Mode Devinettes**
- Afficher une devinette courte (texte + audio) dans la langue cible.
- L'enfant répond oralement ou en choisissant parmi des images.
- Indices progressifs si l'enfant échoue.
- Même système de points et de feedback que le quiz.

**F4 — Mode Course**
- Circuit 3D avec voiture contrôlable (clavier + boutons tactiles).
- Panneaux de signalétique en arabe ou en anglais le long du circuit.
- À chaque panneau, une **consigne** est donnée (audio + texte HUD) : « Tourne à droite », « Va tout droit », « Stop », etc.
- L'enfant doit **s'orienter correctement** pour passer le checkpoint associé et gagner des points.
- Chronomètre et score en temps réel.
- Fin de course : panneau de résultats (points, checkpoints validés, temps).

**F5 — Voix et transcription**
- TTS : lire les consignes, questions et indices dans la langue cible.
- STT : transcrire les réponses orales de l'enfant et les comparer aux réponses attendues.
- Fallback si le micro n'est pas disponible : mode clic uniquement.
- Indicateur visuel quand le micro écoute.

**F6 — Progression et résultats**
- Score cumulé, étoiles par activité, déblocage de nouveaux circuits ou voitures.
- Historique des sessions (date, score, langue).
- Stockage local ; pas de compte obligatoire.

**F7 — Accessibilité et confort enfant**
- Gros boutons, contrastes élevés, animations simples.
- Pas de texte dense ; icônes + audio.
- Possibilité de répéter un son ou une consigne.
- Mode plein écran.

### 3.3 Spécifications techniques

**T1 — Stack**
- **Vue.js 3** (Composition API) + **Vite** + **Pinia**.
- **Three.js** pour la 3D, **Cannon-es** (ou Rapier) pour la physique.
- **browser-whisper** pour le STT (modèle `whisper-base` par défaut, `small` en option).
- **Web Speech API** pour le TTS en v1 ; prévoir une abstraction pour brancher **Kokoro-js** (anglais) et un modèle arabe fine-tuné en v2.
- **IndexedDB** pour les scores, **OPFS** pour le cache des modèles.

**T2 — Assets 3D**
- Tous les modèles 3D sont créés dans **Blender** et exportés en **GLB**.
- Les objets doivent être **nommés de manière stable** pour être référencés dans le code.
- Les panneaux de signalétique peuvent être des **sprites 2D** ou des **panneaux 3D** avec texture ; le texte est appliqué via une texture générée ou un canvas.
- Un **fichier de configuration JSON** décrit le circuit : positions des checkpoints, panneaux associés, consignes.

**T3 — Architecture du code**

**T4 — Performance**
- Le chargement initial ne doit pas télécharger les modèles IA : **chargement paresseux** au premier usage, avec un écran « préparation de la voix… ».
- Les GLB doivent être **compressés** (Draco ou Meshopt si nécessaire) et de taille raisonnable.
- La course doit tourner à **≥ 30 fps** sur un laptop modeste ; désactiver les ombres dynamiques si besoin.

**T5 — Confidentialité**
- Aucune donnée audio n'est envoyée à un serveur : tout le STT/TTS tourne localement.
- Les scores restent dans le navigateur (IndexedDB) ; pas de tracking.

### 3.6 Points de vigilance à documenter dans le README

- **TTS arabe** : la Web Speech API fonctionne sur la plupart des navigateurs de bureau, mais la disponibilité des voix arabes varie selon l'OS. Prévoir un message clair si aucune voix arabe n'est détectée, et proposer le mode clic silencieux.
- **STT** : le premier chargement de Whisper prend du temps (téléchargement du modèle). Prévoir une barre de progression et un préchargement depuis le menu.
- **Blender WASM** : ne pas tenter de l'utiliser au runtime ; Blender reste un outil de production d'assets.
